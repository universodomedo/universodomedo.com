Os dois usos do Egress (não confundir)

Transmissão ao vivo — YouTube/Twitch/Facebook: o Egress renderiza uma página do UDM num Chrome headless, encoda e envia RTMP. Aqui existe encode de vídeo, e é isso que o spike mede.

Gravação de sessão NÃO é vídeo. O que o espectador assiste depois é o replay das ações da sala, renderizado pelo próprio UDM, com câmera livre no cenário (o jogo grava o log de ações de cada Partida para isso). O Egress só grava a trilha de voz em Opus — leve, sem encode — para sincronizar com o replay e alimentar o podcast. Gravação de tela/MP4 seria "assistir um grupo jogando RPG", que é exatamente o que estamos abandonando.

Por que isso importa

1) Multi-stream do Streamlabs é pago e o fluxo atual são 4 ferramentas para uma pipeline. 2) Transmitindo pelo próprio UDM, a cena da live é uma página do app — fichas, mapa, UI de jogo. 3) Voz e transcrição já rodam nesta mesma infra: Egress é o terceiro braço, não uma ferramenta nova.

O que já está pronto (código)

Palco (voz em tempo real, papéis, admin, diagnóstico) — funcional. Transcrição ao vivo — validada com usuários reais, zero infra. Teste de áudio 3D — funcional, zero infra. O botão in-app "Iniciar transmissão" (via EgressClient, mesma SDK que a API já usa) foi deixado de fora de propósito: só faz sentido depois do seu veredito de hardware.

Definições

Decisões

São suas — só nos diga o quê

Aqui ninguém decide por você; queremos sua recomendação.

  1. Onde rodar o spike — dev Windows/Docker Desktop (indicativo) ou direto num Linux alvo (definitivo). O ideal é ter o número Linux em algum momento.
  2. Onde versionar o kit — hoje vive fora dos repositórios (infra-spikes/egress-spike/). Branch, repo de infra, formato: sua praia.
  3. Hospedagem futura — o driver de custo é banda, não CPU. Teto projetado (5 palcos, 550 pessoas, áudio-only): 60–120 Mbps sustentado, 8–16 vCPU, ~US$100–200/mês. Hyperscaler é armadilha para SFU (egress a ~US$0,13/GB; sessão de 4h ≈ 150–250 GB). Na mesa: Vultr/DO São Paulo, bare metal BR, Hetzner EU. Escolha sua.
  4. Orquestração em produção — compose, systemd, k8s: como preferir. O spike só prova o hardware.

Respostas prontas para os "mas". Se sobrar alguma objeção fora desta lista, ela é bem-vinda — junto com o número do teste que a sustenta.

"Isso é perda de tempo — OBS/Streamlabs já resolve"

OBS resolve uma tela de um PC de uma pessoa. O objetivo é o servidor transmitir a visão-de-espectador do jogo (página do app com ficha/mapa) sem depender do PC de ninguém, para múltiplos destinos, e gravar a voz de toda sessão automaticamente. Nada disso o OBS faz sozinho — e o multi-stream do Streamlabs é assinatura paga que queremos matar.

"Por que não usar LiveKit Cloud / um serviço pronto?"

O Cloud cobra por minuto de participante e de egress — vira custo recorrente permanente. Self-host é Apache 2.0, grátis, e o SFU já roda self-hosted hoje servindo a voz do Palco. O spike existe exatamente para saber se o nosso ferro aguenta o pedaço que falta antes de qualquer decisão de gasto.

"Docker Desktop no Windows não mede nada"

Concordo — por isso o número Windows está marcado como indicativo e a Decisão 1 é sua: se preferir rodar direto num Linux, melhor ainda, vira número definitivo de uma vez. Mas um indicativo hoje vale mais que um definitivo nunca.

"Isso não escala / vai cair no meio da live"

Pode ser! É exatamente o que o spike responde com número em vez de achismo. O teto de projeto é conhecido (5 palcos, 550 pessoas, 60–120 Mbps) e o encode de vídeo só existe durante transmissão ao vivo — gravação de sessão é audio-only (Opus), quase grátis. Se o número disser "não dá", ganhamos essa informação pelo preço de 40 minutos.

"Não tenho tempo pra isso"

Hands-on real: ~40 min. Metade é pull de imagem e 10 minutos olhando um stream rodar — dá para fazer em paralelo com outra coisa. O entregável são 3 números num formulário que já monta o relatório sozinho (topo da página).

"Depois vão me pedir pra manter mais um monstro"

Produção é a Decisão 4 — orquestração do seu jeito. E o "monstro" são 3 containers stateless + Redis: sem banco novo, sem deploy de aplicação, sem migração. O app já fala com o LiveKit hoje; só entra um worker do lado dele.

O kit completo — esta página se basta: crie uma pasta, cole estes 6 arquivos (estrutura: raiz + subpasta pedidos/) e siga o Roteiro. Também existe pronto na máquina do Caio em E:\UDM_WORKSPACE\infra-spikes\egress-spike\.

docker-compose.yml

services:
    redis:
        image: redis:7-alpine
        ports:
            - "6379:6379"

    livekit:
        image: livekit/livekit-server:latest
        command: --config /etc/livekit.yaml
        volumes:
            - ./livekit.yaml:/etc/livekit.yaml:ro
        ports:
            - "7880:7880"
            - "7881:7881"
            - "7882:7882/udp"
        depends_on:
            - redis

    egress:
        image: livekit/egress:latest
        environment:
            - EGRESS_CONFIG_FILE=/etc/egress.yaml
        volumes:
            - ./egress.yaml:/etc/egress.yaml:ro
            - ./gravacoes:/out
        cap_add:
            - SYS_ADMIN
        depends_on:
            - redis
            - livekit

livekit.yaml

port: 7880
rtc:
    tcp_port: 7881
    udp_port: 7882
    use_external_ip: false
redis:
    address: redis:6379
keys:
    devkey: devsecret

egress.yaml

redis:
    address: redis:6379
api_key: devkey
api_secret: devsecret
ws_url: ws://livekit:7880
insecure: true
